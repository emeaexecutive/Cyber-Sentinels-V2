# Validation Roadmap and Proprietary AI Boundary

## Position

Cyber Sentinels coordinates provider-backed verification signals, governance
review, replayable evidence and workflow trust posture.

It is not a single detection model. The current product does not claim
proprietary deepfake or biometric AI, universal authenticity, biometric
certainty or guaranteed fraud detection.

## Why Not Proprietary AI First

Detection is one input to an enterprise decision. A detection result without
its source, operating conditions, workflow context, reviewer action and later
audit trail is not sufficient trust infrastructure.

Starting with orchestration and governance allows Cyber Sentinels to:

- use specialist providers where appropriate;
- preserve the source and limitations of each evidence item;
- normalize provider states without hiding provider identity;
- route uncertain or conflicting evidence to accountable human review;
- replay why trust changed and what action followed;
- replace or add providers as technology and policy requirements evolve.

A proprietary model may become useful later. It should enter the platform as
another versioned, governed signal after suitable data, consent, benchmarks and
review protocols exist.

## What Works Now

- workflow trust orchestration;
- replayable evidence and chronology;
- verification receipts;
- governance review concepts and protected workflows;
- provider abstraction and normalized provider signals;
- operational trust posture;
- deterministic, explainable rule-based scoring;
- Supabase-backed records when the environment is configured;
- protected routes, RLS patterns and admin separation.

These capabilities demonstrate application and workflow behavior. They do not
prove the accuracy of a biometric, liveness, deepfake or fraud model.

## What Is Partially Real

- trust scoring;
- trust continuity;
- replayable operational trust;
- workflow orchestration across all intended integrations;
- persistent trust memory at enterprise scale;
- ATS and provider integration coverage.

These areas have code, interfaces or controlled scenarios, but still require
pilot evidence, integration completion or scale validation.

## What Requires Validation

- deepfake detection accuracy;
- biometric certainty claims;
- fraud precision metrics;
- adversarial robustness;
- false positive and false negative rates;
- performance across demographic, device and environmental conditions;
- enterprise-scale trust-graph behavior.

No metric should be published without a defined dataset, sample size, provider
and model version, threshold, environment, reviewer protocol and retained
outcomes.

## Provider Strategy

Cyber Sentinels does not need to own every identity, liveness, biometric,
device-risk or provenance model. Provider adapters can normalize:

- verification state;
- evidence references;
- provider version and operating context;
- confidence or quality fields when supplied;
- missing, pending and failed states;
- risk flags and workflow limitations.

Provider output remains attributed. It contributes evidence but does not
silently become the final enterprise decision. Governance, authorization
lineage, replay and receipts remain part of the decision record.

Configured credentials are not proof of live provider health or accuracy.
Provider-backed testing exists only when an actual provider result is attached
to the test or workflow evidence.

## Measurable Validation Roadmap

1. **Provider-backed test cases**
   Exercise successful, pending, failed and unavailable provider results with
   retained references and known provider versions.

2. **Synthetic candidate simulations**
   Run controlled applicant, proxy-interview and evidence-mismatch scenarios.
   Label every result as simulated.

3. **Injected-session simulations**
   Test channel, device, browser, interruption and session-integrity changes,
   then verify governance and replay behavior.

4. **Real user pilot tests**
   Run consented workflows with named operators, documented conditions and
   accountable review.

5. **False positive and false negative tracking**
   Define the target event, threshold and ground-truth protocol before counting
   outcomes. Retain reviewer overrides and disagreements.

6. **External benchmark comparisons**
   Compare provider or future model signals using representative published or
   independently governed datasets. Report limitations with results.

7. **Proprietary model research only after data exists**
   Confirm lawful data access, consent, security, representativeness and an
   evaluation protocol before model development.

## Benchmark Plan

Every benchmark should record:

- question being tested;
- dataset source and permitted use;
- sample size and class distribution;
- environmental and device conditions;
- provider or model name and version;
- decision threshold;
- false positive and false negative definitions;
- precision, recall and other relevant measures only when supported;
- human-review and disagreement protocol;
- known exclusions and limitations;
- test date and reproducible evidence references.

Build checks, deterministic scenario success and configured provider adapters
are product-readiness evidence. They are not detection-accuracy benchmarks.

## Future Proprietary AI Path

If evidence supports a proprietary signal, development should proceed in
bounded stages:

1. define a narrow enterprise workflow question;
2. establish lawful and representative data;
3. create a baseline against providers and simple rules;
4. evaluate offline with reproducible benchmarks;
5. test adversarial and distribution-shift conditions;
6. pilot as a non-authoritative signal with human review;
7. version outputs and retain them in replay;
8. publish limitations before broader use.

The model must not bypass governance or become a universal score about a
person. Cyber Sentinels remains the orchestration, evidence and accountability
layer around the decision.
