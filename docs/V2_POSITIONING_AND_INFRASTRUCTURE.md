# V2 positioning and infrastructure audit

Reviewed 2026-09-28 for PR #109 closure. This is a source and retained-evidence audit of IAM positioning, personal-agent governance requirements and infrastructure productivity. It creates no personal agent, connector, plugin, paid dependency or operational service. Release, migration and Production proof results must be recorded separately after those actions occur; this document does not predict their success.

Current implementation evidence takes precedence over historical strategy documents. Companion reports: [runtime/API audit](V2_RUNTIME_ALIGNMENT_AUDIT.md), [backoffice audit](V2_BACKOFFICE_AUDIT.md), [provider readiness](V2_PROVIDER_READINESS.md) and [Production proof matrix](V2_PRODUCTION_PROOF_MATRIX.md).

## IAM model and category

The preferred category is **Execution Authorization / Execution Trust for Autonomous Agents**. **Machine Identity + Authority Control Plane** is an accurate secondary architectural description when its execution and integration limits are stated.

Cyber Sentinels is machine/agent identity aware, authority aware, delegation aware, policy enforced and revocation aware. It evaluates target/action authorization and preserves evidence, receipts and Replay. The implemented control is bounded by the request paths and enforcement points that actually call it. A canonical ALLOW does not prove that a destination executed successfully or that arbitrary tools are intercepted.

Cyber Sentinels is not a workforce IAM replacement, SSO directory, HR identity directory, password manager or conventional enterprise IAM suite. Those are category exclusions, not a proposal to delete useful authentication or identity context. Supabase provides the application's current login/session boundary; Cyber Sentinels evaluates the separate authority to perform a consequential agent action.

| Capability | Current implementation | Claim boundary |
| --- | --- | --- |
| Machine/agent identity | Canonical [Operational Entities](../lib/operational-entities/operational-entity.ts), native [Ed25519 proof](../lib/operational-entities/native-verification.ts), API-key principal/tenant binding in [public V1 runtime](../lib/public-api/v1/runtime.ts). | Registration, an authenticated session and credential possession do not create authority. Legacy machine-identity OAuth/certificate fields include explicitly named placeholders. |
| Authority and delegation | Current Trust Contract and authority graph; [native delegation](../lib/operational-entities/delegated-authority.ts) checks subset scope, signed acceptance, expiry, parent lineage and revocation. | A provider role/group or ID token cannot substitute for a current tenant-bound authority grant. |
| Purpose, target, action and policy | [Canonical transaction](../src/lib/trust-transaction/canonical.ts), purpose lineage and [external-effect boundary](../src/lib/trust-fabric/external-effect-boundary.ts). | Tool permission does not authorize every target, credential, channel or purpose. Context and uncertainty must not create synthetic ALLOW. |
| Revocation | Current authority/delegation state is checked during governed evaluation; retained Production proof includes a native authority ALLOW followed by revocation and DENY. | This does not prove immediate cancellation of an in-flight third-party operation, provider token revocation, remote process termination or universal kill-switch coverage. |
| Evidence, receipts and Replay | Existing canonical persistence and immutable decision-time lineage in [server dependencies](../lib/trust-transaction/server.ts); later outcomes/reviews remain separate. | Provider assertions, client assertions and independently verified evidence retain distinct provenance. Replay is reconstruction, not renewed execution permission. |

Historical documents sometimes use broad identity-governance or scoring language. Treat those as context for their named workflows; the canonical ALLOW / REVIEW / DENY path is the execution decision authority. Do not turn identity-governance dashboards, consensus signals or benchmark projections into additional final decision engines.

## Upstream enterprise identity integration points

The following is an integration boundary map, not a connector availability announcement. Source inspection found no native Entra or Okta connector, SAML assertion consumer, SCIM provisioning endpoint or general OIDC-token ingestion route for canonical agent requests. The pilot setup's SAML/OIDC/SCIM choices record readiness/preferences; they do not install or qualify federation. The ordinary auth callback exchanges application authentication sessions and is not evidence of an arbitrary enterprise IdP connector.

| Source / protocol | Appropriate role | Existing seam | Unimplemented or unqualified work |
| --- | --- | --- | --- |
| Microsoft Entra | Upstream human/workload identity and attributable claims. OIDC ID tokens concern authentication; access tokens concern their intended resource. [Microsoft token guidance](https://learn.microsoft.com/en-us/entra/identity-platform/id-tokens). | Canonical entity external identity references and authenticated tenant context. | Selected tenant/app registration, issuer/audience/signature/expiry validation, immutable subject-to-tenant mapping, account linking, lifecycle/revocation evidence and real deployment qualification. No Microsoft directory or workload federation synchronization is claimed. |
| Okta | Upstream authentication and OAuth resource-access grants; [Okta's protocol overview](https://developer.okta.com/docs/concepts/oauth-openid/) distinguishes OIDC identity from scoped API access. | Same provider-neutral identity-reference and server-context seams. | Customer authorization-server configuration, claim contract, tenant binding and lifecycle proof. An Okta group claim alone does not mint a Cyber Sentinels authority grant. |
| OIDC / OAuth | OIDC can supply authenticated identity claims; OAuth can grant bounded access to a particular service. Tokens and claims remain source evidence or transport authorization at the relevant boundary. | Application authentication plus provider-specific implementations; Judge.me OAuth is a documented future installation path, not a live one. | A generic trusted federation adapter is not built. A future adapter needs approved issuers, state/nonce/PKCE where applicable, appropriate audience/resource validation and protected credentials, following [OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700). Never accept a caller-selected tenant from an unverified claim. |
| MCP | Tool discovery/calling transport and, where used, transport authorization. [MCP authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization) does not replace application-specific purpose/target/action policy. | Bounded [OpenGraph canonical composition](../src/lib/opengraph/workflow.ts), authenticated V1 API and execution-authorization artifact. | No deployed generic MCP gateway or qualified OpenGraph executor. Connect a specific server/tool only after transport authentication, target confinement, dispatch binding and normalized outcomes are proven. |
| Other enterprise IdPs / SAML / SCIM | Upstream workforce identity, membership or lifecycle data where a customer requires it. | Pilot configuration and canonical identity-reference vocabulary. | No qualified SAML/SCIM runtime established. Provisioning/deprovisioning must map to an existing tenant and trigger separately governed authority review/revocation; identity deletion alone is not proof all outstanding actions stopped. |

The required composition remains: validated upstream identity/claims -> canonical actor and tenant -> current authority/delegation -> purpose, target and requested action -> canonical policy -> ALLOW / REVIEW / DENY -> separately controlled execution/outcome -> evidence, receipt and Replay. External identifiers remain attributable references; [provider independence](architecture/PROVIDER_NEUTRAL_EVIDENCE_INDEPENDENCE.md) keeps the canonical entity identity under Cyber Sentinels control.

The public enterprise readiness wording must describe a deployment gate to verify, rather than imply completed SSO/SCIM integration. The optional pilot selections and machine-identity sample credentials must retain their explicit readiness/demo labels. No site repositioning to generic IAM is needed.

## Personal-agent governance support and gaps

**Strategy: Cyber Sentinels should govern personal agents, not become another personal agent product.** No standalone assistant, calendar/email connector, booking service or personal-agent UI is built by this work. A future “Personal Agent Authority Profile” would be a workflow template over existing primitives after concrete demand and executor qualification, not a new decision engine.

| Personal-agent requirement | Existing support | Remaining gap |
| --- | --- | --- |
| Identity and accountable owner | Native AI-agent registration, signed manifest/proof and canonical owner/tenant context. | Consumer/personal-account onboarding and ownership semantics have not been qualified. Existing enterprise ownership must not be bypassed to make a demo work. |
| Delegated authority | Signed, bounded parent/child scope, acceptance, policy version, expiry and revocation. | No personal authority-profile template or self-service consent experience. Each connector must bind the actual remote account to the owner and authority. |
| Purpose and target | Purpose lineage; exact action/tool/target/environment constraints; additional URL/domain restriction in the bounded OpenGraph workflow. | Provider-specific resource semantics such as calendar ID, mailbox, recipient or booking account need trusted resolution and enforcement at dispatch. Public reachability is not target authority. |
| Tool/action separation | Permitted action/tool lists plus external effects distinguish data reads/writes, artifact creation/publication and external communication. | No qualified calendar, mail, booking or payment executor. Generic action strings cannot prove remote permission enforcement. |
| Data and communication scope | Delegated data-boundary levels and credential/channel references; native evidence minimization. | Per-item data selection, recipient allowlists, attachment handling and downstream retention controls need a specific service contract. A data label is not a DLP system. |
| Spending and execution limits | Delegated scope has `financialLimit` and `executionLimit`; evaluator compares the supplied action amount/count. | No currency, billing period, aggregate budget, atomic spend reservation or settlement reconciliation. The server converts caller-supplied amount/count with `Number()` and absent values default in evaluation; authoritative finite/nonnegative amounts and concurrency-safe accounting are not established. This is not an enforceable “spend up to EUR X” product. |
| Approval before sending | Canonical REVIEW is non-executing; existing review/adjudication and fresh decision flow preserve the original decision. | No email approval/send transaction or exactly-once dispatch. Approval must bind content digest, recipient, destination and current authority, then pass a fresh governed dispatch check. |
| Evidence / receipt / replay | Canonical immutable decision, outcome separation, linked evidence and Replay; historical idempotent replay cannot mint a new authorization artifact. | Real destination outcomes for personal services remain unqualified. An authorization receipt must not be presented as a sent email, completed booking or settled purchase. |
| Revocation | Future governed evaluations check revoked parent/child authority and expiry. | Instant universal third-party cancellation is unproven. Dispatch races, outstanding execution artifacts, provider tokens and already committed remote effects require explicit integration semantics. |

The delegation [server path](../lib/operational-entities/delegated-authority-server.ts) explicitly supplies an unconfigured external executor. The [synthetic interaction boundary](architecture/SYNTHETIC_INTERACTION_TRUST.md) also holds consequential purchase/refund/payout/approval/promotion requests for REVIEW when the required executor and destination bindings are absent. These safeguards are reasons to keep spending/booking examples as future templates, not claims of live capability.

Examples of future profile intent, all currently **unqualified as external workflows**:

- “Read this calendar”: bind owner, remote account/calendar, read action and permitted data; calendar executor is missing.
- “Draft email, ask before sending”: separate artifact creation from communication and bind approval to the exact send request; mail executor is missing.
- “Spend up to EUR X / book within constraints”: require currency-aware budget reservation and authoritative price/booking outcome; financial and booking execution are missing.
- “Use these services only; revoke delegation”: restrict tool, target, account, credential and channel; re-evaluate revocation before dispatch. No claim of cancelling effects already completed remotely.

No new table, scope or generic primitive is justified solely by these examples. Existing primitives should be reused; proven executor-specific correctness gaps must be resolved before activation.
