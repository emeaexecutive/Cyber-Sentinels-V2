# Enterprise Readiness Scorecard

This scorecard is an internal readiness view. It should not be used as a public performance or accuracy claim.

| Area | Score | Current state | Evidence | Remaining work | Investor/customer risk | Next action |
| --- | ---: | --- | --- | --- | --- | --- |
| Vision | 8 | Cyber Sentinels is positioned as an operational Trust Intelligence layer for humans, AI agents, machine identities, evidence, governance and regulated workflows. | Public homepage, platform, trust center, replay and governance surfaces emphasize replay, posture, authority and enterprise ownership. | Keep category language consistent as new demos and docs are added. | Drift back toward broad detector or dashboard language could dilute enterprise clarity. | Keep homepage and enterprise narrative anchored on operational trust, replay, governance and sovereignty. |
| Architecture | 7 | Core facades consolidate platform health, normalized evidence, trust posture, graph explanation, provider orchestration and ML validation. | `lib/core/platform-health.ts`, `lib/core/evidence-normalizer.ts`, `lib/core/trust-engine.ts`, `lib/core/trust-graph.ts`, `lib/providers/provider-orchestrator.ts`. | Continue reducing duplicate utilities and route-specific trust calculations. | Parallel logic could reappear if future features bypass canonical facades. | Route new trust/evidence/provider work through the canonical core modules first. |
| Runtime | 7 | Runtime execution is staged, event-aware and compatible with async side effects. | `lib/runtime/trust-execution-pipeline.ts`, event bus, parallel signal runner and trust workflow executor. | Add more retained latency evidence under real provider traffic. | External provider latency can degrade runtime confidence. | Capture p50/p95 provider, replay and governance timing during pilot workflows. |
| Replay | 8 | Replay is durable operational memory that preserves evidence, authority, governance and outcomes. | Replay writer, replay pages, receipt flows and trust execution pipeline references. | Keep normalized evidence references attached to replay records wherever possible. | Missing replay references weaken explainability. | Attach normalized evidence IDs and replay references to every material trust update. |
| Governance | 7 | Human review, escalation, restore actions and reviewer accountability remain central. | Governance dashboard, queue hooks, reviewed outcomes and trust posture lifecycle. | Tighten evidence-to-review linking in every protected workflow. | Unresolved governance actions must not be displayed as trust completion. | Require reviewer identity, reason and outcome for overrides and restore actions. |
| Validation | 6 | Validation supports dataset readiness, reviewed outcomes, provider comparison, benchmark metadata, calibration readiness and drift tracking without fabricated metrics. | `lib/core/ml-validation-engine.ts`, `lib/validation/benchmark-harness.ts`. | Increase reviewed labelled cases and benchmark version history. | Precision, recall or F1 claims remain invalid until calibration is complete. | Use `Validation incomplete — insufficient reviewed dataset.` until reviewed calibration evidence exists. |
| ML | 5 | The product separates Real ML, Provider API, Heuristic Baseline, Awaiting Credentials and Not Implemented. | Detection status admin surfaces and validation engine source separation. | Add approved labelled datasets before first-party ML claims. | Overclaiming model capability would create enterprise trust and compliance risk. | Keep first-party ML claims disabled until trained inference and reviewed benchmarks exist. |
| Providers | 6 | Providers are abstracted through readiness and orchestration layers with normalized evidence, state, confidence, latency, credential state and limitations. | `lib/providers/provider-orchestrator.ts`, `lib/providers/provider-readiness.ts`. | Validate one endpoint-specific live provider path with audit logging, timeouts and replay evidence. | Credentials alone can be mistaken for production readiness. | Exercise one live provider workflow with timeout isolation, restricted-data review and normalized replay evidence. |
| Datasets | 5 | Dataset readiness exists, but calibration remains bounded by sample thresholds and reviewed outcomes. | Dataset registry, benchmark harness and validation dashboard. | Build labelled, reviewed, versioned validation sets. | Sparse data prevents reliable performance claims. | Build a reviewed validation set across media, session, document, agent and credential scenarios. |
| Performance | 6 | Runtime uses provider timeouts, cache usage and async side effects in key paths. | Trust execution pipeline provider latency summary and trust cache writes. | Add profiling evidence for slow queries, replay writes and provider calls under load. | Performance confidence remains limited until production-like measurement exists. | Memoize expensive readiness summaries and profile dashboard/admin query paths before adding infrastructure. |
| Security | 7 | Admin-only and protected surfaces remain gated; provider and ML internals are kept out of public claims. | Middleware, Supabase auth patterns, protected admin pages and explicit public limitations. | Continue RLS and admin access checks when adding operational views. | Public exposure of internal telemetry or weakened RLS would damage trust posture. | Keep health and provider diagnostics admin-only and preserve auth, magic links and reset-password flows. |
| UX | 7 | Public UI centers TrustOps, AI Trust Infrastructure, replay, governance, sovereignty and operational trust. | Homepage keeps the operational trust control plane line; platform and trust pages emphasize regulated workflows. | Continue removing candidate-heavy or implementation-heavy wording from general public surfaces. | Crowded or inconsistent terminology can make the platform feel less enterprise-ready. | De-emphasize internal dashboard language on public pages and keep CTAs focused on enterprise access and replay. |
