# ATS Integration Readiness

## Scope

Cyber Sentinels includes a generic ATS integration boundary for candidate events, verification workflow triggers, trust posture context, replay links and verification receipt export.

This layer does not claim a live integration with Greenhouse, Lever, Workday, Ashby, SmartRecruiters or ATLAST/Atlas unless the required server configuration exists and provider-side behavior has been validated.

## Provider abstraction

The provider contract lives in `lib/integrations/ats/` and separates:

- provider status and capabilities;
- webhook normalization;
- signed inbound event processing;
- bounded receipt export;
- replay and receipt references.

The generic adapter prevents provider-specific assumptions from leaking into trust workflows. A provider-specific implementation can be added later only after its API documentation, authentication model and account access are verified.

## Status model

The admin page at `/admin/integrations/ats` uses five explicit states:

- **Connected** — server-side credentials and a receipt endpoint are configured;
- **Webhook configured** — signed inbound events are configured, but outbound API access is not connected;
- **Awaiting API credentials** — enablement was requested but credentials are absent;
- **Placeholder** — only the generic adapter contract exists;
- **Disabled** — the provider is explicitly disabled.

“Connected” reflects server configuration, not a guarantee that a provider account, scope or remote endpoint is healthy. Provider-side validation is still required before production use.

## Supported ATS providers

- Greenhouse
- Lever
- Workday
- Ashby
- SmartRecruiters
- ATLAST / Atlas, only if documented API access exists

ATLAST and Atlas webhook identifiers are normalized to the internal `atlas` provider ID. The adapter remains a placeholder until real API access is verified.

## Signed webhook receiver

`POST /api/integrations/ats/webhook` accepts:

- `candidate.created`
- `candidate.updated`
- `interview.scheduled`
- `interview.completed`
- `offer.created`
- `verification.requested`

Required headers:

- `x-ats-provider`
- `x-ats-event` when the event type is not present in the body
- `x-cyber-sentinels-signature`

The signature is an HMAC-SHA256 hex digest of the exact request body. A provider-specific webhook secret is preferred; `ATS_WEBHOOK_SECRET` is the controlled fallback.

The receiver:

1. rate-limits the request;
2. rejects unknown providers and event types;
3. rejects missing or invalid signatures;
4. normalizes candidate and interview references;
5. checks the audit history for duplicate event IDs;
6. creates or updates the linked workflow record;
7. records an audit event without storing the raw payload.

Only normalized identifiers and event chronology metadata are retained.

## Candidate verification trigger

A `verification.requested` event creates a pending verification event connected to the candidate profile. It does not fabricate a trust score or completed verification receipt.

An `offer.created` event creates an in-review governance action. This gives operators a decision checkpoint without automatically approving or rejecting the candidate.

## Trust posture and replay links

The webhook response calculates contextual trust posture from recorded receipt and governance state. It returns replay and receipt links only when those records already exist and a valid application origin is configured.

Missing replay or receipt data is returned as `null`, not replaced with demo records.

## Outbound verification receipt export

`POST /api/integrations/ats/receipts/[id]/export` is admin-only. It:

1. requires an existing verification receipt;
2. loads a linked replay when available;
3. builds a bounded export payload;
4. refuses delivery unless the selected provider is `Connected`;
5. posts only to the server-configured endpoint;
6. writes an audit event without recording credentials or raw provider output.

The request body identifies the provider and may include workflow, candidate, trust posture and governance references. The receipt and replay URLs are always generated by Cyber Sentinels from existing records.

## Configuration

Each provider uses server-only variables following this pattern:

- `ATS_<PROVIDER>_ENABLED`
- `ATS_<PROVIDER>_API_KEY`
- `ATS_<PROVIDER>_WEBHOOK_SECRET`
- `ATS_<PROVIDER>_RECEIPT_ENDPOINT`

Examples use `GREENHOUSE`, `LEVER`, `WORKDAY`, `ASHBY`, `SMARTRECRUITERS` and `ATLAS` as the provider segment.

Secret values are never displayed by the admin page, returned from APIs or written to audit metadata.

## Security boundaries

- Webhook writes use the service role only after signature verification.
- Receipt export uses the service role only after authenticated admin verification.
- Existing auth and RLS policies remain unchanged.
- Raw webhook bodies and raw provider outputs are not persisted.
- Receipt generation remains evidence-bound.
- Trust posture is contextual and explainable, not a perfect fake/real determination.
- Governance review remains human-authoritative.
