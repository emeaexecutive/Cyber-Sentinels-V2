Audit date: 2026-09-27. Scope: the V2 alignment branch, its canonical execution path, database migrations, API families and the read-only Production observations collected during this run. This report distinguishes source implementation, local regression results and Production evidence. A route file, an enabled RLS flag or a passing source assertion is not a live qualification result.

**Release conclusion: SQL REQUIRED = YES.** Four exposed internal `SECURITY DEFINER` writers have a proven privilege gap. The forward migration in this branch closes their direct-call privileges; it has **not** been applied to Production. Production remains blocked on that correction and its post-application verification. No Production rows, settings or applied migration history were changed during this audit.

## Actual canonical execution order

The implementation is `executeCanonicalTrustTransaction` in `src/lib/trust-transaction/canonical.ts`, with server dependencies in `lib/trust-transaction/server.ts`. The user's conceptual identity → authority → policy → artifacts sequence describes dependencies, **not the literal order of every function call**.

The implemented sequence is:

1. Validate bounded action identifiers, purpose, target, digest and idempotency key; authenticate the actor; derive tenant from trusted session/API principal.
2. Resolve an existing idempotent transaction. It is historical evidence only, must represent the same actor/subject/action/purpose/target/environment/digest, and must have its required persisted artifacts. It is not a fresh authorization.
3. Resolve the Operational Entity and Trust Object with tenant/subject consistency. Collect configured normalized evidence when the entity is active and accountable. **Evidence collection precedes authority resolution** because the decision consumes that evidence.
4. Load the current authority. Evaluate applicable external-effect and purpose-lineage boundaries; check current evidence freshness and authority action/target/environment/purpose bounds; load the exact policy version and optional previous transaction.
5. Produce the one canonical ALLOW / REVIEW / DENY record, with frozen decision-time context and provider-evidence provenance. A delegated request first has its separate signed lineage/subset gate; that gate feeds this same canonical decision rather than a second final engine.
6. Persist the canonical decision, extend the existing Evidence Graph, append Replay, and write Trust Memory when the change is material. **These are awaited before downstream dispatch.** They are separate RPC operations; the whole pipeline is not claimed to be one database transaction.
7. Request external execution only for ALLOW. Store an acknowledgement separately from a terminal SUCCEEDED / FAILED / UNKNOWN outcome. Return the minimized receipt after those stages. An absent relay is `NOT_CONFIGURED`, and REVIEW/DENY is `NOT_REQUESTED`.

`evaluateStoredDelegatedAction` in `lib/operational-entities/delegated-authority-server.ts` disables the generic external relay for the delegated evaluation path. It records the delegation gate, canonical transaction and native enforcement decision binding. Neither that binding nor an ALLOW alone proves a destination action occurred.

## Decision invariants and failure cases

| Requirement | Evidence and precise result |
| --- | --- |
| IDENTITY != AUTHORITY | Native credential/manifest/challenge verification establishes identity evidence. `loadAuthority` separately loads `trust_contracts`; the public API projects identity and authority state separately. Delegation expiry/revocation tests preserve the delegate's identity while removing authority. |
| AUTHENTICATED != AUTHORIZED | `resolveIdentityEnterprise` checks workspace owner/membership and allowed roles after `auth.getUser`; API keys are hash-checked, scoped and rechecked against their owner's current membership. Canonical actor authentication cannot replace authority/policy evaluation. |
| VALID_CREDENTIAL != VALID_PURPOSE | `validateAuthorityScope` requires exact `authorizedObjective === action.purpose`; delegation checks additionally bound purpose and workflow. Optional purpose-lineage evaluation can further restrict the result. |
| PREVIOUS_ALLOW != CURRENT_ALLOW | New requests reload authority, evidence and exact policy; previous state is comparison/lineage only. `previousAllowStandingAuthorization` is false. Historical idempotent retries do not reevaluate or execute and now cannot renew an execution artifact. |
| TOOL_AUTHORIZED != EVERY_TARGET_AUTHORIZED | A bounded `authorityScope` checks requested action, exact target and environment. Delegation checks tool/action/target and non-amplification. The optional external-effect boundary additionally binds destination, effect, credential and channel. Legacy contracts without a bounded scope must not be advertised as having universal target restrictions. |
| PROVIDER_EVIDENCE != CANONICAL_DECISION | Configured normalized evidence is collected with provider IDs, event IDs, timestamps and digests. `agent_asserted` and `unconfirmed` evidence cannot satisfy positive decision eligibility; client evidence namespaces cannot impersonate providers. Provider outcome stays an input to the canonical evaluator. |
| RISK_SIGNAL != AUTOMATIC_DENY | Forecasts, twins, scores, model-state evidence and provider signals are inputs/projections. Policy, authority and explicit evidence conditions decide the canonical result. Tests cover a forecast recommendation outside the deployment gate without directly replacing canonical ALLOW. |
| ALLOW != PROOF_DOWNSTREAM_EXECUTION_SUCCEEDED | `returnSafeTransactionReceipt` exposes separate requested, acknowledgement, outcome references and explicit terminal/unknown/unconfigured states. API outcome assertions remain AGENT_ASSERTED unless independently confirmed. |
| Missing authority or policy | Server resolution throws `AUTHORITY_NOT_FOUND` / `POLICY_VERSION_NOT_FOUND`; no synthetic ALLOW and no dispatch. Such a request can fail before a canonical transaction exists, so the product must not promise a persisted DENY receipt for every malformed/unresolvable request. |
| Revoked, expired, not-yet-valid or mismatched authority | Current revocation state and issue/expiry timestamps are checked with action, target, environment and purpose; invalid authority routes to non-executing canonical DENY. Current-state and delegated-parent rechecks have dedicated regressions. |
| Delegation limits | Signed Alpha delegation and independently signed Beta acceptance; tenant-bound parents; subset checks over actions, targets, tools, purpose, environment, data/financial/execution limits; expiry, depth and cycle restrictions. Database gate locks/rechecks current delegation and parent before storing an evaluation. Production delegation execution was not established in this run. |
| Provider absence/failure | Insufficient decision-eligible evidence yields REVIEW; required database resolution failures throw. Optional legacy-provider lookup may use already-loaded valid baseline evidence when that optional lookup fails; this is neither synthetic evidence nor proof of that provider's availability. A provider outage is not claimed to force DENY independently of policy. |
| Persistence failure | Each awaited persistence failure stops later dispatch. Partial rows may remain because the stages are separate RPCs. Incomplete idempotent receipts now fail closed; recovery/reconciliation is not implemented by silently rerunning downstream effects. |
| REVIEW and DENY | `requestExternalExecutionIfAllowed` returns before the execution dependency unless decision is ALLOW. Public execution authorization returns null for both decisions. REVIEW is a governed stop/review state, not provisional permission. |
| Request retries | Tenant/idempotency uniqueness and transaction advisory lock, semantic request comparison, and concurrent duplicate re-read prevent reuse with a different action or redispatch. Nonce/timestamp controls for signed evidence are separate from decision idempotency. |
| Decision immutability | Canonical decisions and snapshots are preserved through the application API. Snapshot/lineage SQL triggers reject changes to their frozen columns; event and external request/ack/outcome history has append-only triggers. The trusted service role can maintain projection columns. This is not a claim of immutability against a database owner or arbitrary privileged SQL. |
| Outcome review/adjudication | `decision_outcome_review` retains original decision/reasons/policy separately from human override, provider/runtime/destination outcome and adjudication. SQL/TypeScript validate original-decision consistency. `attach_canonical_decision_outcome_review_v1` appends the governed review event; it does not turn a previous REVIEW/DENY into an execution permission. |

Primary regression sources: `tests/canonical-trust-transaction.test.mjs`, `tests/canonical-trust-transaction-integration.test.mjs`, `tests/authority-runtime-evidence.test.mjs`, `tests/native-delegated-authority.test.mjs`, `tests/native-delegated-authority-integration.test.mjs`, `tests/decision-outcome-review.test.mjs`, `tests/public-api-v1-security.test.mjs` and `tests/public-api-v1-openapi.test.mjs`. Behavioral tests and source/migration assertions are distinguished from live database/provider tests; a filename containing “integration” alone does not prove a live external integration.

### Read-only Production observations

The parent audit queried the current Production catalog/advisors and bounded aggregate integrity counts. Only non-sensitive summaries are reproduced here:

- 243 public tables; all have RLS enabled. There are 116 applied migrations, latest `20260913132642` at the observation time. The new restriction migration is absent from that applied state.
- Four inspected aggregate violations were zero: canonical events without parent transactions, operational incident transaction links without their parents, delegations without parent authority, and cross-tenant parent-delegation links.
- The delegation table is empty. Zero orphan rows in an empty relation is not evidence that Production delegation creation, acceptance, enforcement or revocation works.
- Security advisors reported 28 no-policy INFO findings, six mutable-search-path WARN findings, 53 anon and 56 authenticated `SECURITY DEFINER` warnings, and disabled leaked-password protection. Many callable entries are trigger functions rather than ordinary callable writers; they are not all equivalent exploits.
- Function-body/effective-privilege inspection isolated the four ordinary writers in the P0 finding. Core canonical persistence/execution RPCs were separately verified as service-only. Enabling table RLS does not resolve the four exposed writers.

These observations are not a complete referential-integrity proof over all 243 tables. Some canonical references intentionally remain typed IDs/text/JSON and rely on server validation and source lineage rather than universal FKs. The audit did not mutate Production to test negative writes, replay races, owner deletion, or revocation during concurrent execution. The residual advisors, including password protection, remain explicit; no blanket “RLS PASS” or “all security advisors clean” claim is supported.

The required correction is narrowly scoped to proven function execution privileges. It creates no tables or API scopes and does not rewrite applied migrations. Applying it later requires verifying effective privileges in the target catalog and checking the internal trigger workflows. Supabase documents the separate function-execution privilege boundary and the owner-privilege behavior of security-definer functions in [Database Functions](https://supabase.com/docs/guides/database/functions); table policy coverage is described in [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security).

### Legacy sources and UI truth

`lib/operational-trust/api.ts` deliberately reads `verification_receipts`, `trust_timeline_events`, `evidence_chains`, `governance_actions` and generic `trust_replay_sessions`, using bounded newest windows restored to chronological presentation. It reports `hasMore` / continuation requirements. Those older records do not become canonical V2 transactions merely because they appear under a trust-related route.

Similarly, the legacy Agent Registry, public badge fixtures, HPG/Origin/Reality analysis demonstrations and compliance export placeholder are not canonical native verification or execution enforcement. `/api/compliance/export` returns a draft/placeholder response and does not generate a real signed export. The mock badge verification response is removed by this branch. No obsolete table or column was dropped: live dependencies and retention obligations were not established sufficiently to justify removal.
