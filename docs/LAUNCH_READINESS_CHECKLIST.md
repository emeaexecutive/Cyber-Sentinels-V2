# Launch Readiness Checklist

## Readiness standard

Cyber Sentinels is launch-ready for controlled enterprise pilots, investor
walkthroughs and design-partner evaluation when the product can demonstrate a
coherent workflow using recorded evidence without overstating provider,
scoring, biometric or autonomous capabilities.

This checklist describes repository and build readiness. It does not replace
deployment-environment, Supabase-dashboard, email-delivery or live-provider
verification.

## Provider status

- **Hopae Connect:** connected code path when explicitly enabled and all
  server-side credentials are configured. Assurance uplift remains bounded and
  never auto-approves a workflow.
- **Cloudflare Turnstile:** connected to protected public forms. Production
  submissions fail safely when configuration or verification is unavailable.
- **World ID:** authenticated placeholder intake only. Provider exchange is not
  connected and returns `501`; it does not report verification success.
- **Stripe Identity:** placeholder for identity verification. Stripe billing
  integration is separate and must not be described as Stripe Identity.
- **Persona and Entrust:** future adapter placeholders.
- **Fingerprint/device risk:** placeholder signal; no live provider call.

Provider responses are normalized and scrubbed before operational APIs expose
them. Raw provider outputs and secrets remain server-side.

## Trust engine status

- Deterministic and rule-based.
- Dimension weights and signal contributions are explainable.
- Governance affects workflow outcome and authorization continuity.
- Signal direction handling is bounded and tested.
- Assurance levels are code-derived and consent-gated.
- No biometric certainty, trained-model accuracy or universal trust claim.
- No invented replay score movement: numeric change is shown only when a source
  record contains a score.

## Replay status

- Protected replay detail and replay explorer compile.
- Chronology links timeline, evidence, governance, provider signals and
  receipts.
- Replay views are read-only.
- Replay is treated as canonical operational evidence, but the product does not
  claim database immutability.
- Missing replay linkage is represented as unavailable or pending rather than a
  manufactured URL.

## Governance status

- Governance pages and APIs require authentication where appropriate.
- Admin APIs use the established admin guard.
- Reviewer assignment, resolution notes, workflow subject and timestamps remain
  visible.
- Human review remains authoritative.
- General trust-alert and certification APIs remain owner-scoped.

## Trust Center and posture status

- `/trust-center` is protected by verified-session middleware.
- Receipt-backed provider evidence uses `issued_at`, the canonical receipt
  timestamp.
- Trust posture shows strengthening, degradation, staleness, context shifts and
  governance intervention without binary pass/fail UX.
- Empty states explain what has not yet been recorded.
- No synthetic trend scores are generated by the shared trust journey.

## Validation status

- The protected validation lab distinguishes simulation, rule-based evaluation,
  provider-backed evidence and unvalidated capabilities.
- Provider failures, repeated anomalies, replay continuity and governance
  escalation have deterministic scenarios.
- Validation results are not presented as detection benchmarks.
- Provider normalization, receipt continuity, assurance gates and Hopae
  assurance have focused automated tests.

## API status

- Posture, workflow trust, replay, receipt, governance and provider-status APIs
  compile.
- Operational endpoints require a Supabase session and use the caller’s
  RLS-bound client.
- Responses retain existing fields and now include `schemaVersion` and
  `generatedAt` metadata.
- Error responses are generic and versioned.
- Governance pagination is bounded and handles malformed limits safely.
- Raw receipt evidence snapshots are removed from responses.
- Replay references are nullable when no replay exists.

## Authentication and security status

- Existing Supabase session, verified-email and admin-cookie architecture is
  unchanged.
- No RLS policy was weakened.
- No migration, table or database column was added in this phase.
- Production Trust API access fails closed when its API key is absent.
- Runtime validation includes protected-route and Operational Trust API
  inventory checks.

## UX and product consistency

- Shared wordmark, navigation and CTA hierarchy are in place.
- Major surfaces use operational trust, workflow trust, replayable evidence,
  governance continuity, trust posture, session integrity and provider-backed
  verification consistently.
- Replay language no longer claims unsupported immutability.
- Core demo surfaces provide explicit empty states.
- Admin-only validation tooling is not exposed from the standard Trust Center.

## Known limitations

- Live provider health and accuracy are not proven by build-time validation.
- World ID, Stripe Identity, Persona, Entrust and device-risk integrations are
  not production identity-verification paths.
- API keys are a lightweight foundation, not tenant-scoped credential
  infrastructure with rotation, quotas and request signing.
- Rate limiting is process-local and requires durable infrastructure before
  broad public API exposure.
- Email confirmation, SMTP delivery, redirect allowlists and production
  environment variables require deployment-level verification.
- Assurance levels are code/config/API concepts only; they are not persisted in
  new database columns.
- Visual regression automation and independent detection benchmarking remain
  future validation work.

## Pilot readiness

Ready for controlled pilots when:

- a named workflow and reviewer are configured;
- provider status is described accurately;
- evidence, governance, replay and receipt steps are demonstrated end to end;
- pilot operators understand simulation versus provider-backed evidence;
- deployment auth, email and environment checks are completed;
- feedback and support ownership are assigned.

The recommended pilot story remains: workflow entry, provider evidence, session
change, governance escalation, replay reconstruction, receipt generation and
updated trust posture.

## Investor and design-partner readiness

The repository supports a credible walkthrough of the current product:

- operational trust posture across workflows;
- replay as canonical evidence chronology;
- human-reviewable governance;
- normalized provider orchestration;
- portable verification receipts;
- explicit ethical and technical boundaries.

Present proven product behavior separately from provider roadmap, benchmarking
and future integration work. Do not imply perfect detection, biometric
certainty, surveillance coverage or autonomous final authority.

## Validation commands

Before each launch candidate:

```text
npx tsc --noEmit
npm run test:hopae
node --experimental-strip-types --test tests/trust-assurance.test.mjs tests/provider-hardening.test.mjs tests/receipt-verification.test.mjs
npm run build
```
